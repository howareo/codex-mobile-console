# 维护、配置变更与服务重启

## 先分清：网页服务和任务服务是分开的

| 服务 | 负责什么 | 更新什么时才需要动它 |
|---|---|---|
| 4174 手机网关 | 网页、登录、Codex 协议转发、Claude 转发 | 网关后端代码更新。仅网页资源更新通常刷新页面即可 |
| 4500 Codex app-server | Desktop 与手机共用的 Codex 执行进程 | Codex 程序升级，或它需要重新加载的运行配置变化 |
| 4600 Claude 后端 | Claude 历史与手机发起的 CLI 任务 | Claude 后端代码或 SDK 更新；会影响手机正在运行的 Claude 任务 |
| 看门进程 | 发现缺失服务、配置变化、安装升级，安排维护窗口 | 看门 PowerShell 脚本更新，需要重新启动看门本身 |

只更新手机网页或网关，不需要重启 4500。重启 Desktop 窗口也不等于重启独立的 4500。

## “配置待重载”不等于“正在重启”

待重载只表示磁盘目标与运行进程的已加载记录不同。这个状态本身不应封锁网页。

实际自动重载需要：目标稳定、桌面等直接客户端断开、任务明确空闲，并连续通过两个检查周期。默认检查间隔为 30 秒，另有探测耗时；因此通常要等一分钟以上，不能把它理解为严格的 60 秒倒计时。

桌面仍连接、任务仍运行、任务状态未知时，会继续等待。这是在保护任务，不是“文件还没复制完”。失败默认冷却 300 秒，同一目标最多尝试三次；达到上限后先查原因，不反复点击重启。

真正进入维护后，网关先拦住 Codex 的新接口请求，等待已接受的请求结束，再检查一次空闲状态，才允许停止旧进程。网页、登录、诊断和 Claude 接口继续可用。维护中的请求会明确返回 `CODEX_MAINTENANCE`，不会自动重复发送消息。

## 我没动 CC Switch，为什么仍有配置变化？

CC Switch 不是唯一的配置写入者。Desktop、MCP 插件、Hook 管理工具也会更新配置。例如桌面重启可能更新 MCP 连接目录，信任某个 Hook 会修改其信任记录。这些可能影响工具调用，仍需检测。

目前的分类：

- `config.toml`：比较解析后的实际内容。注释、空白、键顺序，以及六个明确的桌面外观设置不触发重载；其余未知配置保守保留检测。
- MCP 环境变量 `SKY_CUA_NATIVE_PIPE_DIRECTORY` 不触发重载：2026-11-10 对照 Desktop 日志，18 次变化中 17 次紧跟 Desktop 启动；重载 4500 必须先关 Desktop，重启无法追上它。其余 MCP command/env 与 Hook 信任变化仍检测。改算法时已确认磁盘配置与 4500 已加载记录一致（旧算法指纹相同），再用新算法重建已应用基线，旧记录备份在当次 incident 目录。
- `auth.json`：只保存摘要，不记录凭据值；单独修改密钥仍会被发现。
- 模型目录、指令文件、Hook 文件：继续检测；尚未改成只检测当前模型引用，以免遗漏 profile 使用的文件。
- Codex 程序：另有安装发现、稳定观察、bundle 校验与待切换记录。相同版本号也可能是不同二进制，以运行进程路径及内容哈希为准。

语义指纹算法首次启用时，旧基线与新基线可能不同，需要一次正常维护重载。程序不会把磁盘的新指纹冒充成当前进程已加载的配置。

## 打不开或发送失败时怎么做

1. 双击根目录 `codex-mobile.cmd`，先选**查看状态**和**诊断**，看具体等待原因。
2. 若只有手机网关异常，使用菜单的**重启手机网关 4174**。这不应重启共享 4500。
3. 若确实需要让 Codex 加载新配置，先结束需要保留的任务，关闭 Desktop，使用**重启 4500**或下面的等待命令。状态未知时不要强杀。

在项目目录运行：

```powershell
.\scripts\codex-mobile.ps1 status
.\scripts\codex-mobile.ps1 diagnose

# 仅重启手机网关
.\scripts\codex-mobile.ps1 restart-gateway -Apply -Confirmation RESTART_MOBILE_GATEWAY

# 等待客户端退出、任务空闲后，受控重载共享 Codex
.\scripts\codex-mobile.ps1 restart-4500 -Wait -Apply -Confirmation RESTART_4500
```

不要直接启动第二份 app-server，不要修改会话数据库，也不要因为某个 PID 出现在旧文件里就结束它。Windows 会复用 PID。

## 2026-11-10 故障与修复

旧维护标记来自四天前的一次重载超时。它只检查标记中的 PID 是否存在；系统重启后该 PID 被 Windows 服务复用，导致网关误以为仍在更新，连首页与 Claude 都返回 503。移走已确认过期的标记后，首页和会话列表立即恢复，无需重启 4500。

新维护标记由重载脚本在整个事务期间持有 Windows 文件共享锁。进程正常退出或被强制结束，操作系统都会释放锁；仅有残留文件、无效 JSON 或一个存在的 PID 不再代表维护进行中。网关必须确认新标记和在途请求已排空后，脚本才继续。

日志还显示：新 app-server 在几秒内已启动，但父重载脚本未完成，随后达到 240 秒上限。11月6日两次重载时序一致（约 12 秒已应用配置，240 秒被看门结束），与“新 app-server 继承旧代码捕获输出的管道写端、管道永不结束”的机制吻合；现场没有线程栈，仍属高可信推断。代码中原本无界捕获启动脚本输出，现已改为日志落盘、等待该子进程退出，启动检查上限 120 秒；失败进入现有恢复流程，不再依赖输出管道 EOF。

## 2026-11-10 第二批可靠性修复

- 看门对自动重载使用独立的 `ReloadTimeoutSeconds`（默认 420 秒），大于重载脚本自身最坏耗时，不再在回滚中途被 240 秒上限结束；启动检查仍为 240 秒。
- 回滚启动原版本后先等端口监听并通过 `readyz`（最多 20 秒），再做协议验证，避免把“尚未就绪”误记为恢复失败。
- 只有已停止旧进程的重载失败才写回待切换记录；并发重载中被拒绝的一方不再用旧快照覆盖。
- 网关在途计数在处理函数完成（onSend）时扣除，手机中途断开的请求不再让维护确认永远等待。已用测试证明旧逻辑会遗留计数。
- 维护判断只认文件共享冲突（EBUSY）；权限或只读错误不再退回到会被 PID 复用欺骗的检查。
- 维护期间收到实时订阅时以 1013 关闭连接，手机自动重连并重新订阅，不再静默丢弃。
- 维护、来源检查改在 websocket 插件之后注册；被拒绝的握手会释放底层连接，网关关闭不会被挂住。
- 免登录私网模式下，Codex 写接口与 `/api/events` 拒绝与当前页面来源不一致的浏览器请求（没有 Origin 的本机工具不受影响）。
- `/api/healthz` 增加 `upstream`（网关到 4500 的连接状态）与 `maintenance`；看门日志把网关状态区分为“正常 / 存活-维护中 / 存活-上游未连接 / 缺失”，只记录不自动重启。

## 诊断证据与已知边界

- `.runtime/autostart.log`：中文看门日志、真实配置变化键、等待原因。
- `.runtime/stack-events.ndjson`：重载各阶段及失败记录；`reload-ensure.*.stdout.log` / `stderr.log` 保存启动检查输出。
- 手机诊断接口 `/api/diagnostics/status`：连接状态、待重载信息及 `maintenance.active`；`/api/healthz` 报告网关存活、到 4500 的连接与维护状态，但不等于模型上游可用。
- 已应用记录、待重载记录和待版本切换记录用途不同，不通过删除 pending 文件来假装加载成功。
- 网关是用户选择的私网免登录模式。可访问此入口的设备能操作会话；它不应暴露公网。
- 目前仍保守监控全部模型目录文件及指令/Hook 变化。逐项确认官方热加载行为后，才能继续减少需要重载的类型。

本次核验覆盖实际 Windows 文件锁、进程被终止后的释放、维护期间路由隔离、子进程超时边界、配置语义摘要。没有为验证而重启生产 4500，也没有改 provider、密钥、模型目录或会话库。Opus 咨询请求被当前上游拒绝（所选模型不可用），本说明不是 Opus 已审通过的结论。
